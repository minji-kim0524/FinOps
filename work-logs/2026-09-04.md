### 목적 및 이유
- 사용자가 "현재 작업 중인 파일들의 가독성을 높이고 중복을 제거해달라"며 5가지 기준(단일 책임 분리, 중복 로직 공통화, 변수/함수명 명확화, 불필요한 import·Dead Code 제거, 리팩토링 후 무동작-변경 검증)을 명시적으로 요청. 이 세션 동안 계속 커진 `backend/app/main.py`(519줄)와 `frontend/src/App.jsx`(752줄)가 각각 인증·급여계산·이력조회·집계 등 여러 책임을 한 파일에 담고 있어 가장 먼저 손봐야 할 대상이었음
- **백엔드**: `main.py`를 앱 조립(CORS, rate limit 예외 핸들러, 헬스체크, 라우터 등록)만 남기고 42줄로 축소. Pydantic 스키마는 `schemas.py`로, DB 세션을 다루는 순수 계산/직렬화 로직은 `services/records.py`로, HTTP 엔드포인트는 도메인별로 `routers/auth.py`·`routers/records.py`로 분리. 기존에 `_` 접두사로 "비공개"였던 함수들(`_serialize`, `_apply_calculated_fields`, `_save_calculated`, `_get_record_or_404`, `_build_summary`, `_validate_password_strength`)은 모듈 간에 공유해야 해서 접두사를 떼고 의도가 드러나는 이름(`serialize_record`, `apply_calculated_fields`, `save_calculated_records`, `get_owned_record_or_404`, `build_group_summary`, `validate_password_strength`)으로 바꿈
- 라우터 분리 시 `/records/export`, `/records/summary` 등 정적 경로가 `/records/{record_id}` 같은 동적 경로보다 반드시 먼저 등록돼야 한다는 FastAPI/Starlette의 라우팅 규칙을 인지하고, 기존 `main.py`의 등록 순서를 그대로 유지해 라우팅 충돌을 예방. pytest 전체 통과 후에도 실제 서버를 띄워 `/calculate`, `/records`, `/records/export`, `/records/summary`, `/records/{id}/payslip`, PUT/DELETE `/records/{id}`까지 curl로 직접 재확인
- **프론트엔드**: `App.jsx`에서 데이터/상태 로직 전체(이력·집계 조회, 페이지네이션, 필터, CSV 업로드, 엑셀/명세서 다운로드)를 `hooks/useSalaryRecords.jsx` 커스텀 훅으로 추출해 "컨테이너(데이터)"와 "프레젠테이션(화면)"을 분리. 인증 만료 시 로그아웃 처리하는 `reportError` 로직은 훅과 컴포넌트 양쪽에서 필요해 `hooks/useErrorReporter.js`로 별도 추출
- 중복 제거: `handleExport`/`handleDownloadPayslip`이 토씨 하나 다르지 않게 반복하던 blob 다운로드 로직을 `utils/download.js`의 `downloadBlob`으로, 거의 동일하던 월별/연도별/직원별 집계 fetch 3개 함수를 공통 헬퍼(`fetchAndStore`)로, 구조가 완전히 같던 집계 표 3개(월별/연도별/직원별)를 `components/SummaryTable.jsx` 하나로 통합
- 계산 폼(`CalculateForm`)·CSV 업로드/엑셀 버튼(`BulkActions`)·필터 바(`RecordFilters`)·수정 모달(`EditRecordModal`)·비밀번호 변경 모달(`ChangePasswordModal`)·차트 2종을 각각 독립 컴포넌트로 분리하고, 표 컬럼 정의(`buildRecordColumns`, `buildSummaryColumns` 등)도 `tableColumns.jsx`로 분리. `buildColumns`는 집계용 `buildSummaryColumns`와 헷갈리지 않도록 `buildRecordColumns`로 개명
- 커스텀 훅에서 필터 값이 바뀔 때마다 1페이지로 되돌리던 기존 동작(`onChange` 안에서 `setPage(1)`도 함께 호출하던 부분)을 그대로 보존하기 위해, 훅이 `updateSelectedEmployee`/`updateDateRange`/`updateMinGrossPay`/`updateMaxGrossPay`처럼 "값 변경 + 페이지 초기화"를 함께 수행하는 세터를 노출하도록 설계 — 검색어는 기존처럼 디바운스 이펙트가 페이지 초기화를 담당
- 검증: 백엔드 pytest 77개, 프론트엔드 vitest 14개, `npm run build`, `oxlint`(신규 미사용 import/변수 없음) 전부 통과. 실제 서버·프론트 기동 후 회원가입→계산→수정→명세서 확인까지 브라우저에서 시도했으나, 세션의 브라우저 자동화 도구가 모달 내 입력 조작에서 간헐적으로 불안정하게 반응해 신뢰도 있는 결과를 얻지 못함 — 대신 Playwright E2E 4개(회원가입→계산→**수정**→삭제→로그아웃, 페이지네이션, 비밀번호 재설정, 모바일 가로스크롤)를 재실행해 전부 통과하는 것으로 "수정" 등 핵심 흐름이 리팩토링 후에도 그대로 동작함을 확인
