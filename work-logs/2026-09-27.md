# 2026-09-27

## (커밋 없음) 이력 조회 쿼리 DB 인덱스 점검 — 측정 결과 인덱스를 추가하지 않기로 결정

- 코드 변경 없음. 측정과 판단 근거를 남기기 위한 기록

### 목적 및 이유
- AskUserQuestion으로 제시한 후보(비밀번호 재설정 보안 답변 방어, 이력 조회 쿼리 DB 인덱스 점검) 중 사용자가 "이력 조회 쿼리 DB 인덱스 점검"을 선택. `salary_records`에는 `id`와 `owner_id`에만 인덱스가 있고, 이력 목록의 필터·정렬에 쓰이는 `created_at`/`employee_name`/`gross_pay`에는 인덱스가 없다는 점에서 출발. 다만 "있어야 한다"가 아니라 "실제로 효과가 있는지 먼저 측정한 뒤 적용 여부를 판단"하는 것으로 범위를 잡음
- 어제(2026-09-26) 집계 API 작업과 같은 방식으로 임시 PostgreSQL 클러스터(`initdb`/`pg_ctl`)를 띄워 **배포 DB 방언**에서 측정. 임시 스크립트(scratchpad, 프로젝트 코드 아님)로 사용자 20명 중 한 명에게 5만 건(전체 14.5만 건), 이어서 극단적으로 한 명에게 30만 건(전체 39.5만 건)을 몰아 넣고, 실제 서비스 코드(`apply_record_filters`/`apply_record_sort` + `count` + `offset/limit`)로 이력 조회 1페이지에 해당하는 쿼리를 시나리오별로 5회 측정해 최소값을 비교
- 후보 인덱스는 필터/정렬 패턴에 맞춰 `(owner_id, created_at)`, `(owner_id, employee_name)`, `(owner_id, gross_pay)` 복합 인덱스 3개

### 측정 결과 (PostgreSQL, 이력 조회 1페이지, 인덱스 없음 → 있음)
| 조회 | 사용자 5만 건 | 사용자 30만 건 |
|---|---|---|
| 기본 목록(id순) | 2.55 → 2.51 ms | 7.14 → 7.17 ms |
| 정렬 created_at desc | 4.49 → 2.57 ms | 14.56 → 7.01 ms |
| 정렬 gross_pay desc | 4.83 → 2.54 ms | 14.95 → 6.97 ms |
| 정렬 employee_name asc | 4.79 → 2.49 ms | 15.05 → 7.25 ms |
| 직원 필터(=) | 2.24 → 0.51 ms | 7.23 → 0.66 ms |
| 기간 필터(1개월) | 2.27 → 0.49 ms | 6.98 → 0.94 ms |
| 급여 범위 필터(좁게) | 2.62 → 0.42 ms | 8.58 → 0.72 ms |
| 이름 검색(ilike) | 5.91 → 5.74 ms | 17.53 → 17.36 ms |

### 결정: 인덱스를 추가하지 않음
- 인덱스 없이도 한 사용자 5만 건에서 2~6ms, 극단적인 30만 건에서도 최악 약 17ms로 이미 충분히 빠름. 이 앱(직원 급여 계산 이력)의 현실적인 규모에서는 병목이 아님
- 인덱스로 얻는 이득은 정렬 약 2배, 선택적 필터 약 5~10배지만 절대값으로는 요청당 몇 ms 수준. 반면 인덱스 3개는 저장/수정 때마다 쓰기 비용과 저장 공간이 늘고 마이그레이션도 하나 더 생김
- 이름 검색(`ilike '%…%'`)은 앞쪽 와일드카드 때문에 일반 btree 인덱스를 못 타서 인덱스를 추가해도 어차피 개선되지 않음. 개선하려면 `pg_trgm` 같은 별도 확장이 필요한데 그럴 만한 근거는 없음
- 같은 성능 작업인데도 집계 API(1,053ms → 30ms, 약 35배)는 적용했고 이건 적용하지 않은 이유: 집계는 요청마다 전체 이력을 메모리로 올려 O(N)으로 늘어나는 구조적 문제였던 반면, 목록 조회는 이미 페이지네이션+`owner_id` 인덱스를 타고 있어 측정해보니 개선 여지가 작았음
- 이력이 사용자당 수십만 건 단위로 늘어나는 사용 패턴이 실제로 생기면 그때 위 측정 방식(임시 PostgreSQL + 시나리오별 측정)으로 다시 점검할 것
- 측정에 쓴 임시 PostgreSQL 클러스터와 스크립트는 작업 후 정리했고 저장소에는 변경이 남지 않음
