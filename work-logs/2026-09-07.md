### 목적 및 이유
- 지금까지는 세전 급여(정기 급여) 한 항목만 입력받을 수 있었는데, 실제 급여명세서에는 상여금/성과급이 자주 함께 등장한다는 점에서 계산 항목을 확장. AskUserQuestion으로 제시한 후보(로그인 보안 강화, 백엔드 테스트 커버리지 측정, 상여금/성과급 항목 추가) 중 사용자가 이 항목을 선택
- **계산 로직**: 상여금은 같은 달 세전 급여와 함께 지급되는 경우로 가정해, 4대보험료·소득세(국세청 간이세액표 조회) 모두 `세전 급여 + 상여금`을 기준으로 계산하도록 `calculate_net_pay`를 수정. 저장되는 `gross_pay` 컬럼 자체는 원래 입력값을 그대로 유지하고, 실수령액만 합산액 기준으로 계산해 "얼마를 받았는지"와 "정기 급여가 얼마였는지"를 구분해서 남김. 소득세 조회는 `lookup_income_tax`를 건드리지 않고 `df.assign(gross_pay=total_pay)`로 조회용 임시 컬럼만 바꿔치기하는 방식으로 최소 변경
- `bonus_pay`는 기본값 0이라, 기존에 상여금 없이 저장된 데이터·테스트는 모두 이전과 동일한 값을 낸다. 실제로 기존 pytest 77개는 수정 없이 그대로 통과했고, 엑셀 export 컬럼 목록이 바뀐 테스트 1개만 새 컬럼에 맞게 갱신
- **DB 마이그레이션**: `salary_records`에 `bonus_pay` 컬럼을 추가하는 Alembic 마이그레이션을 autogenerate로 생성. 기존 행을 위해 `server_default='0'`을 그대로 유지하는 방식을 선택했는데, 처음에는 자동 생성된 대로 `server_default`를 넣었다가 이후 `alter_column`으로 제거하려 했으나 SQLite가 `ALTER COLUMN ... DROP DEFAULT`를 지원하지 않아 마이그레이션이 중간에 실패하는 것을 확인 — batch 모드 없이도 두 DB(SQLite 로컬/PostgreSQL 운영)에서 모두 동작하도록 `server_default`를 영구히 남겨두는 더 단순한 형태로 수정
- **집계**: 월별/연도별/직원별 집계의 "총 세전 급여"가 상여금을 포함한 실제 세전 총 지급액을 의미하도록 `build_group_summary`에서 `gross_pay + bonus_pay`를 합산 대상으로 변경
- **프론트엔드**: 계산 폼·수정 모달에 "상여금/성과급" 입력 필드 추가, 이력 표에 컬럼 추가, "세전 급여 vs 실수령액" 차트의 세전 급여 막대가 상여금을 포함한 금액을 표시하도록 `dataKey`를 함수로 변경, CSV 업로드 버튼 안내 문구에 `bonus_pay` 컬럼 추가(모바일 레이아웃은 이전에 처리한 줄바꿈 CSS 덕분에 문구가 길어져도 가로 스크롤이 생기지 않음을 확인)
- 검증: pytest 83개(기존 77 + 상여금 관련 신규 6개), vitest 14개, `npm run build`, oxlint 모두 통과. 로컬에 실제 백엔드·프론트엔드를 띄워 curl로 계산/급여명세서 PDF/엑셀 내보내기까지 직접 확인했고, Playwright E2E에 상여금 전용 시나리오(계산 → 이력 표 표시 → 수정 모달 값 유지)를 추가해 5개 전부 통과. 마지막으로 브라우저에서 직접 로그인해 이력 표·월별/연도별/직원별 집계 화면까지 육안으로 최종 확인
- E2E/수동 테스트 도중 `/auth/register`·`/auth/login`의 분당 5회 rate limit(slowapi)에 여러 번 걸려 일부 테스트가 일시적으로 실패했는데, 이는 코드 버그가 아니라 같은 IP에서 회원가입을 반복 실행한 테스트 절차 자체의 영향이었음 — 로컬 백엔드를 재기동(메모리 기반 rate limiter 초기화)해 재현·해소했고, 그 과정에서 로컬 SQLite DB 파일을 지운 뒤 마이그레이션을 다시 적용하지 않아 "no such table: users" 오류가 발생한 것도 원인 중 하나였음을 확인해 정상화
