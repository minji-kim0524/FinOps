## `7f6f699` fix. 이력 표 정렬을 서버 사이드로 전환 - 컬럼 정렬이 현재 페이지(10건)에서만 동작하던 문제를 /records의 sort_by/sort_order 파라미터로 해결(허용 컬럼 화이트리스트, id 보조 정렬로 페이지 안정성 확보) - 프론트엔드는 sorter: true로 위임하고, 정렬이 실제로 바뀔 때만 1페이지로 리셋 - pytest 93개(신규 4개)/vitest 14개 통과, 실제 브라우저에서 페이지 경계 넘는 정렬 유지 확인

- 수정 파일: `backend/app/routers/records.py`, `backend/app/services/records.py`, `backend/tests/test_records_pagination.py`, `frontend/src/App.jsx`, `frontend/src/hooks/useSalaryRecords.jsx`, `frontend/src/tableColumns.jsx`

### 목적 및 이유
- AskUserQuestion으로 제시한 후보(이력 표 정렬 서버 사이드 전환, 로그인 보안 강화) 중 사용자가 이 항목을 선택. 어제 고친 엑셀 내보내기 필터 버그와 같은 계열의 문제로, 이력 표가 서버 사이드 페이지네이션으로 전환된 이후 각 컬럼의 정렬(`antd` `sorter`)이 여전히 클라이언트 비교 함수로 남아 있어 실제로는 "현재 페이지(10건) 안에서만" 정렬되고 전체 이력 기준 정렬은 되지 않던 것을 코드로 직접 확인
- **백엔드**: `app/services/records.py`에 정렬 허용 컬럼을 화이트리스트(`SORTABLE_RECORD_FIELDS`)로 관리하는 `apply_record_sort(query, sort_by, sort_order)`를 추가. `sort_by`가 화이트리스트에 없으면(오타·존재하지 않는 컬럼 등) 기존 기본 정렬(`id` 오름차순)로 안전하게 폴백하도록 해, 임의 문자열로 `getattr(SalaryRecord, ...)`를 호출하는 것을 막음. 값이 같은 행이 여러 개일 때 페이지 간 순서가 흔들리지 않도록 `id`를 항상 보조 정렬 기준으로 추가
- `/records` 엔드포인트에 `sort_by`/`sort_order` 쿼리 파라미터를 추가하고, 기존 `.order_by(SalaryRecord.id)`를 `apply_record_sort(...)` 호출로 교체
- **프론트엔드**: `tableColumns.jsx`의 각 컬럼에서 `(a, b) => ...` 형태의 클라이언트 비교 함수를 `sorter: true`로 바꿔 정렬을 서버에 위임(antd 표준 서버 사이드 정렬 패턴). `useSalaryRecords.jsx`에 `sortBy`/`sortOrder` 상태와 `updateSort(field, antdOrder)`를 추가해 `/records` 요청에 반영하고, `App.jsx`의 `Table`이 `pagination.onChange` 대신 최상위 `onChange(pagination, filters, sorter)`로 페이지·정렬 변경을 한 곳에서 받도록 통합
- 까다로웠던 부분은 "정렬이 실제로 바뀐 경우에만 1페이지로 되돌리고, 순수 페이지네이션 클릭(정렬 불변)일 때는 페이지를 유지"하는 조건 처리였음 — `updateSort`가 이전 정렬 상태와 새 정렬 상태를 비교해 값이 같으면 아무 것도 하지 않도록 해, 페이지 클릭 시 정렬이 의도치 않게 1페이지로 리셋되는 것을 방지
- 검증: pytest에 오름차순/내림차순 정렬, 페이지 경계(2페이지)를 넘어도 전체 이력 기준 정렬이 이어지는지, 잘못된 컬럼명이 기본 정렬로 폴백하는지 확인하는 테스트 4개 추가 — 93개 전부 통과, 커버리지 99% 유지. vitest 14개·build·oxlint도 기존과 동일하게 통과
- 로컬에 급여액이 제각각인 12건(10건 초과로 2페이지 확보)을 만들어 실제 브라우저에서 확인: "세전 급여" 오름차순 정렬 시 1페이지가 최솟값부터 정확히 정렬되고, 2페이지로 넘어가도 정렬이 유지된 채 이어짐(9,000,000원→10,000,000원 순). 이 상태에서 "직원명" 컬럼을 새로 정렬하니 `sort_by=employee_name`으로 바뀌며 1페이지로 정확히 리셋되는 것도 네트워크 요청으로 직접 확인
