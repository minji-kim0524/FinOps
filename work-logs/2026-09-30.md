## `939131f` feat. 급여명세서 ZIP 일괄 다운로드에 건수 제한 추가 - 한 번에 최대 1,000건(실측 근거: 건당 약 4ms, 1,000건 약 3.7초/27MB)로 제한, 초과 시 400과 구체적 안내 반환 - 프론트엔드는 현재 필터 건수가 넘으면 버튼을 미리 비활성화하고 경고 표시, blob 에러 응답 본문도 직접 파싱해 이유 안내 - pytest 109개(경계값 테스트 포함)/vitest 50개 통과

- 수정 파일: `README.md`, `backend/app/routers/records.py`, `backend/tests/test_payslip.py`, `frontend/src/AppContent.jsx`, `frontend/src/components/BulkActions.jsx`, `frontend/src/hooks/useRecordExports.jsx`, `frontend/src/hooks/useRecordExports.test.jsx`

### 목적 및 이유
- AskUserQuestion으로 제시한 두 후보(CSV 일괄 업로드 파일 크기 제한, 급여명세서 ZIP 일괄 다운로드 건수 안내/제한) 중 사용자가 후자를 선택. 필터 없이 이력이 아주 많은 상태로 ZIP을 요청하면 한 요청 안에서 PDF를 건수만큼 전부 생성해야 해 응답이 느려지거나 서버 메모리를 과도하게 쓸 수 있다는 점에서 출발
- 임의로 상한을 정하지 않고, 임시 스크립트(scratchpad, 프로젝트 코드 아님)로 `build_payslip_pdf`를 50/100/500/1,000건 반복 호출해 실제 소요 시간과 ZIP 크기를 먼저 측정: 건당 약 3.6~4ms로 선형 증가, 1,000건 기준 약 3.7초·27MB. 이 실측치를 근거로 상한을 1,000건으로 정함(로컬 macOS 기준이라 Render 같은 공유 CPU 환경에서는 더 걸릴 수 있다는 점을 감안해 여유를 둠)
- `backend/app/routers/records.py`의 `download_payslips_zip`에서 필터를 적용한 뒤, PDF를 만들기 전에 `query.count()`로 건수만 먼저 확인해 상한(`MAX_PAYSLIP_ZIP_RECORDS = 1000`)을 넘으면 400과 함께 "직원·기간 등 필터로 범위를 좁혀주세요" 안내를 반환하도록 함 — PDF 생성 자체를 시작하기 전에 걸러내는 게 핵심(이미 다 만든 뒤에 버리는 방식이 아님)
- **프론트엔드도 실패를 기다리지 않고 미리 안내**: `/records`와 `/records/payslips`가 같은 필터 파라미터를 쓰므로, 이미 화면에 있는 `salary.totalRecords`(현재 필터에 맞는 전체 건수)가 ZIP 엔드포인트가 셀 건수와 정확히 같다는 점을 이용해, 버튼을 누르기 전에 1,000건 초과 여부를 판단해 버튼을 비활성화하고 경고 문구를 보여줌. 백엔드의 `MAX_PAYSLIP_ZIP_RECORDS`와 값을 반드시 맞춰야 하는 상수라 프론트엔드 쪽에도 그 사실을 주석으로 남김
- **까다로웠던 부분**: `downloadPayslipsZip`은 파일을 받기 위해 `responseType: "blob"`으로 요청하는데, 이 설정에서는 axios가 에러 응답의 JSON 본문도 Blob으로 그대로 돌려줘서 `err.response.data.detail`로 바로 읽을 수 없다는 걸 재확인(과거 CSV 업로드 400 처리 때는 이 문제가 없었는데, 그건 JSON 응답 요청이라 axios가 자동으로 파싱해줬기 때문). `readBlobErrorDetail` 헬퍼로 Blob을 텍스트로 읽어 직접 `JSON.parse`하도록 처리하고, 파싱 실패 시를 대비한 기본 안내 문구도 남김
- 검증: pytest에 정확히 1,000건(허용)과 1,001건(거부, 400 메시지에 두 숫자 모두 포함되는지) 경계값 테스트 추가 — 매 건을 `/calculate`로 계산하면 느려서 `bulk_insert_mappings`로 DB에 바로 삽입하는 헬퍼를 씀. 109개 전부 통과(커버리지 99% 유지). vitest 50개(신규 3개: blob 에러 정상 파싱/파싱 실패 시 폴백/기존 500 에러 케이스, jsdom의 `Blob.text()` 지원 여부도 이 테스트로 확인됨), build·oxlint 통과
- 로컬 서버에 실제로 1,001건을 DB에 직접 넣고 브라우저에서 확인: 경고 문구가 뜨고 버튼이 `disabled: true`로 비활성화되는 것을 DOM에서 직접 확인. 검색어로 1건까지 좁히니 버튼이 다시 활성화되고, 실제 클릭 시 `/records/payslips?search=...` 요청이 200 OK로 성공하는 것도 네트워크 요청으로 확인
