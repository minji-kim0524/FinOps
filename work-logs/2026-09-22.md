### 목적 및 이유
- AskUserQuestion으로 제시한 후보(.env.example 파일 추가, 비밀번호 재설정 보안 답변 무차별 대입 방어, 낮은 프론트엔드 커버리지 파일 보강) 중 사용자가 이 항목을 선택. 어제(2026-09-21) 처음 측정한 결과 `src/hooks` 디렉터리가 평균 50.27%였고, 그중에서도 `useRecordExports.jsx`(20.83%)와 `useErrorReporter.js`(20%)가 가장 낮았음 — 둘 다 파일 다운로드·CSV 업로드·인증 만료 처리처럼 실패하면 사용자가 바로 체감하는 로직이라 "위험도 높은 곳"으로 판단
- `useErrorReporter`는 실제로는 React 훅을 내부에서 호출하지 않는 순수 팩토리 함수라, `renderHook` 없이 직접 호출해 401/403 시 로그아웃 콜백이 불리는지, 그 외 상태 코드·네트워크 오류는 폴백 메시지만 보여주는지 검증
- `useRecordFilters`는 `useState`/`useEffect`를 쓰는 진짜 훅이라 `@testing-library/react`의 `renderHook`+`act`로 테스트. 특히 신경 쓴 부분: (1) 검색어는 `vi.useFakeTimers()`로 300ms 디바운스를 직접 진행시켜 지연 반영을 확인 (2) `updateSort`가 "정렬이 실제로 바뀐 경우에만 페이지를 1로 되돌리고, 페이지네이션 클릭처럼 같은 정렬 정보가 다시 들어오면 페이지를 유지"하는 조건 분기를 재현 (3) `buildFilterParams`가 `dayjs` 날짜 범위를 시작일 00:00:00~종료일 23:59:59로 변환하는 부분까지 실제 `dayjs` 객체로 검증
- `useRecordExports`는 `../api`와 `../utils/download`를 `vi.mock`으로 모킹(App.test.jsx에서 쓰던 것과 같은 패턴)해 테스트. 가장 복잡한 `uploadBulkCsv`의 세 가지 분기(전부 성공/일부 성공+실패 행 안내 모달/전부 실패)와, 업로드 요청 자체가 400으로 실패했을 때 백엔드가 준 이유를 그대로 보여주는지, 그 외 상태 코드는 공용 폴백 메시지로 가는지까지 확인. 엑셀/ZIP/CSV템플릿/개별 명세서 다운로드 4종 모두 성공·실패 경로를 각각 테스트
- 1차로 27개를 추가해 전체 57.79%→73.38%까지 올린 뒤, 커버리지 리포트에 남은 몇 줄(다운로드 3종의 catch 블록, `updateDateRange`/`updateMaxGrossPay`의 개별 페이지 리셋)도 비용이 낮고 "필터마다 일관되게 동작하는지" 확인하는 의미가 있어 추가로 채워 75.8%까지 개선
- `App.jsx`, `tableColumns.jsx`, 각종 프레젠테이션 컴포넌트(차트, 모달)처럼 실제 렌더링이 필요한 부분은 이미 Playwright E2E가 상호작용을 검증하고 있고, 단위 테스트로 다시 채우려면 접근 방식 자체가 달라(컴포넌트 렌더링 테스트) 별도 작업 범위라 판단해 이번엔 손대지 않음 — README의 커버리지 설명도 "순수 로직/데이터 훅은 두텁게, 렌더링이 필요한 컴포넌트는 E2E가 담당"으로 현재 상태에 맞게 갱신
- 검증: vitest 47개(기존 20 + 신규 27) 전부 통과, build·oxlint 기존과 동일. 이번 작업은 백엔드를 건드리지 않아 pytest는 재실행하지 않음
