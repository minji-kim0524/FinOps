# 2026-07-28

## `49e25dc` feat. SQLite에서 PostgreSQL로 전환 - docker-compose에 db 서비스 및 healthcheck 추가 - DATABASE_URL 환경변수로 DB 연결 방식 분기 - psycopg2-binary 드라이버 추가

- 신규/수정 파일: `docker-compose.yml`, `backend/app/database.py`, `backend/requirements.txt`

### 목적 및 이유
- **7단계(운영 환경 전환)** 착수: 지금까지 쓰던 SQLite(파일 하나짜리 서랍)를 실제 서비스에 가까운 PostgreSQL(물류창고)로 교체
- `docker-compose.yml`: `db` 서비스(postgres:16-alpine) 추가. Postgres는 컨테이너가 뜬 직후 바로 접속 가능한 상태가 아니라 초기화 시간이 필요하므로, `pg_isready` 기반 healthcheck와 `depends_on: condition: service_healthy`를 걸어 backend가 DB 준비 완료 후에 시작되도록 구성. 데이터는 `db_data`라는 named volume에 저장해 컨테이너를 지워도 보존
- `backend/app/database.py`: 기존에는 SQLite 전용 옵션(`check_same_thread`)을 무조건 적용했는데, PostgreSQL 연결 시엔 이 옵션이 필요 없어서 `DATABASE_URL`이 SQLite인지 여부로 분기 처리. 덕분에 로컬 venv 개발(Docker 없이)은 여전히 SQLite로 그대로 동작하고, Docker 환경에서만 PostgreSQL을 씀
- `requirements.txt`: PostgreSQL과 통신하기 위한 `psycopg2-binary` 드라이버 추가
- 검증:
  - pytest 8개 전원 통과 (로컬 SQLite 경로는 영향 없음 확인)
  - `docker compose up --build`로 db/backend/frontend 3개 컨테이너 정상 기동, backend 로그에서 정상 시작 확인
  - API로 계산 요청 후, `docker compose exec db psql`로 접속해 실제 PostgreSQL 테이블에 데이터가 들어갔는지 직접 조회 확인
  - `docker compose down` → `up` 반복해도 데이터가 유지되는 것 확인 (volume 영속성 재검증)
  - 브라우저에서 프론트엔드 화면에도 정상 표시, 콘솔 에러 없음
  - 확인 후 테스트용 데이터는 `docker compose down -v`로 정리
