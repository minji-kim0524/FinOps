### 목적 및 이유
- 이번 작업은 "다음 작업 진행하자" 흐름이 아니라 사용자가 직접 지시한 보안 작업: "입력 데이터 검증 누락으로 SQL 인젝션, XSS 같은 고위험 보안 취약점이 발생하지 않도록 전체 코드를 검토해서 보완해줘". 막연히 방어 코드를 덧붙이지 않고, 먼저 위험 후보를 코드에서 찾고 → 스크래치패드 재현 테스트로 실제로 뚫리는지 확인 → 확인된 것만 고치는 순서로 진행
- **검토 결과, 우려했던 두 가지는 이미 안전**: ① SQL 인젝션 — 모든 쿼리가 SQLAlchemy ORM 바인딩이고 정렬 컬럼도 화이트리스트(`SORTABLE_RECORD_FIELDS`)라 문자열 조합 SQL이 없음. 인젝션 페이로드(`' OR '1'='1`, `DROP TABLE`, `UNION SELECT` 등)가 데이터로만 취급된다는 점을 회귀 테스트로 고정. ② XSS — 프론트엔드에 `dangerouslySetInnerHTML`/`innerHTML`/`eval` 등이 없고 React가 기본 이스케이프함. 직원명에 `<img src=x onerror=window.__xss=1>`를 저장해 운영 빌드로 띄운 화면에서 글자 그대로 표시되고 `window.__xss`가 설정되지 않음을 DOM에서 직접 확인
- **재현 테스트로 실제 확인된 취약점/결함** (수정 전 상태에서 임시 테스트 실행, 임시 파일은 repo 밖 스크래치패드에서만 사용하고 실행 후 삭제):
  - **PDF 마크업 주입**: `payslip.py`가 직원명을 reportlab `Paragraph`에 그대로 넣어, `<b>굵게`처럼 닫히지 않은 태그가 있으면 500 오류. 이력 한 건의 이름 때문에 ZIP 일괄 다운로드 전체가 실패할 수 있고 `<img>` 같은 태그도 해석 대상. `xml.sax.saxutils.escape`로 해결
  - **엑셀 수식 주입**: openpyxl은 `=`로 시작하는 문자열을 수식 셀(`data_type='f'`)로 기록해, `=HYPERLINK(...)` 직원명이 파일을 여는 사람 PC에서 수식으로 실행될 수 있음. `neutralize_excel_formulas`로 수식으로 잡힌 셀을 문자열(`'s'`)로 되돌림(숫자 컬럼은 원래 수식이 아니라 데이터 변화 없음, 값은 그대로 보존)
  - **범위 검증 누락으로 인한 500**: 급여 음수·10^12·10^30, 존재하지 않는 날짜 형식, `page=10^20`, `record_id=10^20`(SQLite 정수 오버플로), CSV의 `1e30`/`inf`, 72바이트 넘는 비밀번호(bcrypt 5가 예외 발생). 모두 422/401/행 오류로 정리
  - **검증 없이 저장되던 값**: 부양가족 -5, 10만 자 직원명, `<script>alert(1)</script>` 같은 아이디
  - **LIKE 와일드카드**: 검색어 `_`/`%`가 모든 행에 매칭되어 필터가 무력화(인젝션은 아니고 기능 결함). `escape` 인자와 `_escape_like`로 글자 그대로 검색
- **한도 설계 근거**: 운영 DB가 PostgreSQL이고 모델 컬럼이 `Integer`(int4, 최대 약 21.4억)라서, 세전 급여와 상여금 각각 10억(`MAX_PAY_AMOUNT`)으로 잡으면 합계가 21.4억 아래에 머무름(SQLite는 64비트라 로컬 테스트에서는 안 드러나는 문제). 부양가족·자녀 수는 각 50, 직원명은 50자·제어문자(NUL 포함, PostgreSQL 저장 시 오류) 금지. 비밀번호·보안 답변은 bcrypt가 앞 72바이트만 쓰므로 글자 수가 아니라 UTF-8 바이트 수로 검사(한글은 글자당 3바이트라 24자까지). 모든 한도는 `backend/app/limits.py` 한 곳에 모으고 프론트엔드 `limits.js`에 같은 값을 둠(백엔드 쪽이 최종 검증, 프론트는 제출 전 안내용)
- **기존 사용자를 막지 않도록 둔 비대칭**: 아이디 형식 검사는 회원가입에서만 하고 로그인·비밀번호 재설정·보안 질문 조회는 길이 상한(128자)만 둠. 과거에 규칙 없이 가입한 계정이 로그인하지 못하게 되는 일을 피하기 위함(프론트 로그인 화면도 형식 검사를 하지 않는다는 테스트 포함). 72바이트 넘는 로그인 비밀번호는 예외가 아니라 "불일치(401)"로 처리
- **테스트가 잡아준 별개의 기존 버그**: CSV 직원명 열에 빈 칸이 섞이면 pandas가 열 전체를 실수로 읽어 `1234`가 `"1234.0"`으로, 빈 칸이 `"nan"`으로 저장되던 문제를 `test_csv_numeric_and_empty_employee_names_are_stored_as_text`가 발견. 문자열 변환만 덧붙이면 이미 `.0`이 붙은 뒤라 늦으므로 `pd.read_csv(..., dtype={"employee_name": str})`로 읽는 시점에서 해결
- **직전 작업(CSV 파일 크기 제한)의 경계 테스트 보정**: 직원명을 `a`로 채워 정확히 1MB를 만들던 테스트가 새 직원명 길이 제한 때문에 "행 오류 1건"이 되어 `created == 1` 단언이 깨짐. 이 테스트의 목적은 "정확히 한도 크기의 파일은 크기 검사(400)에 걸리지 않는다"이므로 200 + 행 오류 1건으로 단언을 바꾸고 이유를 주석으로 남김
- **다층 방어(보안 헤더/CSP)**: 백엔드는 미들웨어로 `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`를 모든 응답(401 같은 오류 응답 포함)에 부착. 정적 프론트엔드는 `render.yaml`의 `headers`로 같은 헤더에 CSP(스크립트는 같은 출처만, 요청은 우리 백엔드로만, 인라인 스타일만 antd 때문에 허용) 추가. 로그인 토큰이 `localStorage`에 있어 XSS가 생기면 탈취될 수 있다는 점을 감안한 완화책
- **CSP는 실제로 켜서 검증**: 운영 빌드(`VITE_API_BASE_URL=http://localhost:8000`)를 repo 밖 스크래치패드에 따로 빌드하고, 같은 CSP 헤더를 붙이는 임시 정적 서버(5174)와 임시 백엔드(SQLite, alembic 적용)를 띄워 브라우저로 확인: 응답 헤더에 CSP가 있고, 일부러 삽입한 인라인 `<script>`는 실행되지 않으며 콘솔에 CSP 위반이 기록됨(그 1건 외 오류 없음), 엑셀 내보내기·ZIP 다운로드 요청이 200 OK. 첫 시도에서 `127.0.0.1`로 접속해 CORS 출처(`localhost`) 불일치로 OPTIONS 400이 난 것은 주소를 `localhost`로 맞춰 해결(앱 문제 아님). 검증 후 임시 서버·테스트 DB 정리, `git status`는 의도한 파일만 남음. 단, 실제 Render 배포에서의 헤더 적용은 확인하지 못함
- **남겨둔 한계**: CSP의 `connect-src`에 백엔드 주소가 고정되어 있어 주소가 바뀌면 함께 바꿔야 함(`render.yaml` 주석에 명시). JWT를 `localStorage` 대신 httpOnly 쿠키로 옮기는 구조 변경은 범위가 커서 이번에는 하지 않고 사용자에게 한계로만 알림
