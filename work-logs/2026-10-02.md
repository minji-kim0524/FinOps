# 2026-10-02

## `26ee261` feat. CSV 일괄 업로드에 파일 크기 제한 추가 - 한 번에 최대 1MB(실측 근거: 행별 DB 저장이 병목, 1만 행 1.5초/5만 행 8초/10만 행 20초, 1MB면 약 3만 행까지 허용)로 제한, 초과 시 400과 현재/최대 크기 안내 반환 - 멀티파트 파싱 중 채워지는 file.size로 메모리에 읽기 전에 미리 거절, 프론트엔드도 beforeUpload로 네트워크 요청 자체를 막고 즉시 경고 표시 - pytest 111개(경계값 테스트 포함)/vitest 50개 통과

- 수정 파일: `README.md`, `backend/app/routers/records.py`, `backend/tests/test_main.py`, `frontend/src/AppContent.jsx`, `frontend/src/components/BulkActions.jsx`

### 목적 및 이유
- AskUserQuestion으로 제시한 두 후보(CSV 일괄 업로드 파일 크기 제한, 엑셀 내보내기도 동일한 건수 보호 검토) 중 사용자가 전자를 선택. 바로 전 작업(ZIP 다운로드 건수 제한)과 같은 종류의 문제였던, `/calculate/bulk`가 업로드 파일 크기에 아무 제한이 없어 아주 큰 CSV를 올리면 서버가 전체를 메모리로 읽어들이고 처리 시간도 과도하게 길어질 수 있다는 점에서 출발
- 임의로 상한을 정하지 않고, 임시 스크립트(scratchpad, 프로젝트 코드 아님)로 `pd.read_csv` → `parse_bulk_upload_csv` → `save_calculated_records`를 1,000/10,000/50,000/100,000/200,000행에 대해 실제로 돌려 단계별 소요 시간을 측정. 결과는 예상과 달리 CSV 파싱 자체(`read`+`parse`)는 10만 행에서도 0.03초로 무시할 수준이었고, 시간을 지배하는 건 행마다 `SalaryRecord` ORM 객체를 만들어 `db.add_all`+`commit`하는 저장 단계였다(1만 행 약 1.5초, 5만 행 약 8초, 10만 행 약 20초, 20만 행 약 40초 — 행당 약 0.15~0.2ms로 대략 선형)
- 이 실측을 바탕으로, 저장 단계가 응답 시간을 지배한다는 걸 알고 나서도 "파일 크기"라는 사용자가 선택한 지표로 제한을 걸기로 함(요청된 옵션 자체가 파일 크기 제한이었음). 측정한 샘플 CSV가 행당 약 30바이트였던 점을 근거로 1MB≈3만 행을 상한으로 잡았는데, 이는 로컬 기준으로도 수 초 안에 끝나는 수준이라 Render 같은 더 느린 공유 CPU 환경에서도 감당 가능한 여유를 둔 것(직전 ZIP 다운로드 작업 때와 같은 "로컬보다 느릴 수 있으니 여유를 둔다" 원칙 유지)
- `backend/app/routers/records.py`의 `calculate_bulk`에서 `await file.read()`로 파일을 메모리에 전부 읽어들이기 전에, Starlette의 멀티파트 파서가 이미 채워둔 `file.size`를 먼저 확인해 1MB 초과면 400과 함께 "현재 N.NMB, 최대 1MB" 안내를 반환하도록 함 — ZIP 다운로드 때 세운 "비싼 작업을 시작하기 전에 걸러낸다"는 설계를 그대로 따름. `file.size`가 멀티파트 업로드에서는 항상(0으로 초기화된 뒤 파싱되며 채워짐) 설정된다는 걸 Starlette 소스(`starlette/formparsers.py`)를 직접 읽어 확인한 뒤 별도의 None 분기 없이 바로 비교하도록 작성
- **프론트엔드도 실패를 기다리지 않고 미리 거름**: `BulkActions.jsx`의 antd `Upload`에 `beforeUpload` 핸들러를 추가해, 선택한 파일이 1MB를 넘으면 `message.error`로 안내하고 `Upload.LIST_IGNORE`를 반환해 `customRequest`(실제 업로드 요청)가 아예 호출되지 않도록 함. 백엔드의 `MAX_BULK_UPLOAD_CSV_BYTES`와 값을 반드시 맞춰야 하는 상수라 프론트엔드 쪽에도 그 사실을 주석으로 남김(ZIP 다운로드 때의 `MAX_PAYSLIP_ZIP_RECORDS` 패턴과 동일)
- **까다로웠던 부분**: 경계값(정확히 1MB 허용 / 1MB+1바이트 거절) pytest를 추가하다가, `_csv_padded_to_size` 헬퍼로 만든 두 테스트를 기존 `test_calculate_bulk_endpoint_skips_invalid_rows_and_reports_them` 함수 바로 뒤에 삽입하는 과정에서 Edit 도구의 old_string 매칭 범위를 함수 끝보다 짧게 잡는 바람에, 원래 그 함수의 마지막 3줄(`saved = client.get("/records").json()` 이하 저장 건수 검증)이 새로 추가한 두 번째 테스트 함수 본문 안으로 잘못 흡수돼버림. pytest를 돌려 `test_calculate_bulk_endpoint_rejects_when_over_the_size_limit`에서 `saved["total"] == 1` assertion이 실패하는 걸 보고서야 발견했고, 해당 3줄을 원래 함수(`skips_invalid_rows`) 끝으로 되돌리고 새 테스트에서는 제거해 바로잡음 — Edit으로 함수 경계 근처를 수정할 때는 그 함수의 실제 마지막 줄까지 다 읽었는지 재확인해야 한다는 걸 다시 확인
- 경계값 테스트는 `employee_name` 컬럼이 자유 문자열이라는 점을 이용해, 헤더+마지막 행 틀을 고정하고 그 사이를 `"a"` 문자로 패딩해 전체 바이트 수를 `MAX_BULK_UPLOAD_CSV_BYTES`(허용 케이스)와 `+1`(거절 케이스)에 정확히 맞추는 방식으로 작성. 검증: pytest 111개 전부 통과(정확히 1MB는 200·1건 생성, 1MB+1바이트는 400과 메시지에 "너무 큽니다"/"1MB" 포함 확인), vitest 50개·oxlint·프론트 빌드 통과
- 로컬에 임시 백엔드(SQLite, alembic upgrade head로 스키마 적용)를 띄우고 브라우저에서 실제로 1MB+1바이트 CSV를 `input[type=file]`에 `DataTransfer`로 주입해 업로드 시도 → `/calculate/bulk` 요청이 네트워크 로그에 전혀 잡히지 않고 "CSV 파일이 너무 큽니다(현재 1.0MB, 최대 1MB)" 경고만 뜨는 것을 확인. 이어서 제한 이하의 정상 CSV를 업로드해 실제로 `POST /calculate/bulk → 200 OK`가 발생하고 "1건이 일괄 계산되었습니다" 메시지와 함께 표·월별/연도별/직원별 집계에 반영되는 것까지 확인. 검증 후 임시 백엔드 프로세스와 테스트용 SQLite 파일은 모두 정리했고 `git status`도 의도한 5개 파일만 깨끗하게 남은 상태로 확인
