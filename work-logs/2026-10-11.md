## `15d1bbd` chore. 백엔드 의존성 버전 고정으로 재현 가능한 빌드 구성 - constraints.txt로 하위 의존성까지 정확한 버전 고정하고 requirements.txt가 -c로 항상 적용, Dockerfile이 constraints.txt를 함께 복사 - 운영(Python 3.11) 최신 버전과 로컬(3.9) 호환 버전을 python_version 조건으로 구분(3.9 기준 고정 시 starlette·pillow·python-multipart 등 취약 구버전에 묶이는 문제 확인), Linux 전용 하위 의존성(greenlet) 누락 방지를 위해 Docker(Linux)에서 해석하는 scripts/update_constraints.sh 추가 - CI의 pip-audit이 고정 버전을 점검하도록 변경, README에 의존성 고정·갱신 방법 추가 - Linux 3.11·로컬 3.9 양쪽에서 pytest 218개 통과, 운영 이미지 설치 버전 일치 및 /health 기동 확인

- 신규 파일: `backend/constraints.txt`, `backend/scripts/update_constraints.sh`
- 수정 파일: `.github/workflows/ci.yml`, `README.md`, `backend/Dockerfile`, `backend/requirements.txt`

### 목적 및 이유
- AskUserQuestion으로 제시한 세 후보(백엔드 의존성 버전 고정, 비밀번호 변경·재설정 후 기존 토큰 무효화, 아이디 열거 방지) 중 사용자가 첫 번째를 선택. 코드에서 확인한 근거: `backend/requirements.txt`가 패키지 이름만 있고 버전이 전혀 없어 빌드할 때마다 최신 버전이 설치됨. 로컬 가상환경은 Python 3.9.6인데 운영 Dockerfile·CI는 3.11이라 서로 다른 버전을 쓸 수 있고, 상류 릴리스 하나로 배포가 깨질 수 있음(앞서 겪은 bcrypt 5의 72바이트 초과 예외가 그 사례). 실제로 새 가상환경에 설치해 보니 기존 로컬 venv와 이미 버전이 달랐음(pydantic 2.13.4→2.13.5, PyJWT 2.13.0→2.15.1, SQLAlchemy 2.0.51→2.0.54)
- **방식 선택**: 직접 의존성만 `==`로 고정하면 하위 의존성(starlette·pydantic·numpy 등)은 여전히 흔들리므로, 전체를 잠그되 직접 쓰는 목록(`requirements.txt`)은 사람이 읽기 쉬운 상태로 유지하는 "requirements + constraints" 방식을 택함. `requirements.txt`에 `-c constraints.txt` 한 줄만 추가하면 Dockerfile·CI·E2E·README의 기존 `pip install -r requirements*.txt` 명령을 하나도 안 바꿔도 항상 적용됨(pip가 include 파일 기준 상대경로로 해석하는 것을 새 venv 설치로 확인). 대신 Dockerfile은 `constraints.txt`도 함께 `COPY`해야 해서 수정
- **검증 중 발견한 문제 ① — 3.9 기준으로 고정하면 오히려 취약해짐**: 처음에는 로컬(3.9)에서 해석한 버전을 그대로 고정했는데, `pip-audit`으로 점검하니 starlette 5건·pillow 18건·python-multipart 6건(파일 업로드 처리 라이브러리)·anyio 2건·python-dotenv·pytest 등 알려진 취약점이 있는 구버전에 묶였고, 수정판은 전부 Python 3.10 이상에서만 존재. 즉 운영(3.11)이 고정 이전(최신 설치)보다 취약해지는 퇴행. 그래서 운영은 3.11에서 해석되는 최신 버전, 로컬은 3.9에서 가능한 버전으로 나눠 `python_version >= "3.10"` / `< "3.10"` 조건으로 적음(로컬이 3.10 이상이 되면 3.9용 줄은 불필요)
- **발견한 문제 ② — Linux 전용 하위 의존성 누락**: macOS에서 `pip freeze`한 목록으로 만든 이미지를 검사하니 운영 이미지에는 `greenlet`(SQLAlchemy가 Linux에서만 끌어오는 하위 의존성)이 설치되는데 고정 목록에는 없었음 → 그 패키지는 버전이 풀려 있는 상태. 이후 `greenlet==3.5.6`을 임시로 고정했더니 이번엔 이 버전이 Python 3.10+ 전용이라 Linux+3.9(WSL 등)에서 설치 불가가 되고, pip-audit이 파일 전체를 3.9에서 읽다가 실패 → 버전별 조건으로 분리. 같은 이유로 한쪽 Python에만 있는 패키지(`opentelemetry-api`, `exceptiongroup`, `tomli`)에도 조건을 붙이도록 스크립트를 한 번 더 고침. 결론: 잠금 파일은 **운영과 같은 Linux에서 Python 버전별로 해석**해야 정확하므로, 사람이 매번 실수 없이 만들 수 있게 Docker 기반 `scripts/update_constraints.sh`(3.11·3.9 컨테이너에서 각각 설치→freeze→`python_version` 조건으로 병합)를 추가. 스크립트 안에서 `constraints.txt`를 가리키는 `-c` 줄을 뺀 사본으로 설치해 "지금 해석되는 최신 버전"을 얻음
- **실제 고정된 운영(3.11) 버전**: fastapi 0.143.0, starlette 1.7.0, pandas 3.0.6, SQLAlchemy 2.1.4, numpy 2.4.6, pydantic 2.14.0, uvicorn 0.54.0 등 — pandas·SQLAlchemy·starlette가 메이저 변경을 포함. 그동안 테스트는 3.9용 버전으로만 돌았기 때문에, 운영이 실제로 받게 될 이 집합에서 통과하는지를 가장 중요한 검증으로 삼음(고정 없이 지금 운영에 빌드해도 같은 버전이 설치됨)
- **검증**: ① Linux·Python 3.11 컨테이너에서 새로 설치 후 설치 목록이 고정 파일과 완전 일치(환경 조건을 `packaging.markers`로 실제 평가하는 비교 스크립트로 확인 — 처음에 쓴 `comm`은 정렬 문제로 두 번 중단돼 파이썬 비교로 교체)하고 pytest 218개 통과 ② 로컬 Python 3.9에서 새 venv를 고정 목록으로 처음부터 설치해 일치 확인 + pytest 218개 통과 ③ 실제 배포 경로인 Dockerfile로 이미지를 빌드해 설치 37개가 고정 목록과 일치(고정 목록에 없는 설치 항목 없음)하고, 컨테이너를 띄워 alembic 마이그레이션 후 `/health`가 200이며 앞서 추가한 보안 헤더(`x-content-type-options`)가 나오는 것까지 확인 ④ `pip-audit`: 운영(3.11) 고정 버전은 "알려진 취약점 없음", 3.9용 버전은 위 6개 패키지가 구버전에 머묾(수정판이 3.10+ 전용이라 불가피)
- CI(`.github/workflows/ci.yml`): pip-audit이 `requirements.txt`(해석 시점마다 달라짐)가 아니라 `constraints.txt`의 고정 버전을 점검하도록 바꾸고 주석을 현실에 맞게 수정. 빌드를 막지 않는 기존 정책(`|| true`)은 유지 — 고정 버전은 자동으로 오르지 않고, 수정판이 아직 없는 CVE로 무관한 PR이 막히는 것을 피하기 위함. README에 "의존성 버전 고정" 설명과 갱신 방법(`scripts/update_constraints.sh` 후 `git diff`·pytest)을 추가
- **남은 한계/알려둔 점**: 사용자의 기존 로컬 venv는 건드리지 않음(고정 버전과 조금 다르며 `pip install -r requirements-dev.txt`로 맞출 수 있음). 로컬 Python 3.9는 수정판이 없는 구버전이 설치되므로 3.11로 올리는 것을 권장. 3.11 최신 버전 pytest 실행에서 Starlette의 "`TestClient`에서 `httpx` 사용은 폐지 예정, `httpx2` 설치" 경고 1건이 나옴(지금은 동작 영향 없음, 추후 대응 후보). 검증용으로 `python:3.11-slim`·`python:3.9-slim` 베이스 이미지를 새로 받았고(검증용 backend 이미지·컨테이너는 정리), 다음 배포부터는 이전 빌드와 달리 위 버전들이 쓰임
