### 목적 및 이유
- AskUserQuestion으로 "로그인 보안 강화(계정 잠금)"를 이번 세션 동안 열 번 가까이 후보로 제시했었는데, 오늘 처음 선택됨. 기존에는 `/auth/login`에 slowapi로 분당 5회 요청 속도 제한만 걸려 있었는데, 이건 "짧은 시간에 한 IP에서 몰아치는 시도"만 막을 뿐, 여러 IP에 걸쳐 천천히 시도하는 무차별 대입(비밀번호 스프레이 등)은 막지 못한다는 것이 실질적인 보안 공백이었음
- `User` 모델에 `failed_login_attempts`(기본 0)와 `locked_until`(nullable) 컬럼을 추가하고 Alembic 마이그레이션 작성 — 기존 `bonus_pay` 마이그레이션 때와 동일하게 SQLite가 `ALTER COLUMN ... DROP DEFAULT`를 지원하지 않는 제약을 고려해 `server_default='0'`을 영구히 남기는 방식을 그대로 재사용
- `app/auth.py`에 `MAX_LOGIN_ATTEMPTS=5`, `LOCKOUT_MINUTES=15` 상수와 `is_account_locked`/`register_failed_login`/`reset_login_attempts` 헬퍼를 추가. `/auth/login`은 (1) 계정이 잠겨 있으면 비밀번호가 맞든 틀리든 423으로 즉시 차단하고, (2) 그 외에는 기존처럼 비밀번호를 검증하되 실패할 때마다 카운트를 올려 5회째에 15분 잠금을 걸고, (3) 성공하면 카운트를 0으로 초기화하도록 수정
- **테스트에서 까다로웠던 부분**: `MAX_LOGIN_ATTEMPTS`를 5로 정했는데 우연히 기존 slowapi의 "분당 5회" 요청 속도 제한과 같은 숫자라, 같은 분(rate limit 윈도) 안에서는 6번째 요청이 항상 내 잠금 로직(423)보다 먼저 slowapi 데코레이터(429)에 걸려버림 — 즉 계정 잠금이 "요청 속도 제한 창이 넘어간 뒤"에만 실제로 관찰 가능하다는 것을 테스트하며 발견. `tests/test_rate_limit.py`에 이미 있던 "테스트 안에서 `limiter.reset()`을 호출해 요청 속도 제한 창을 새로 시작한 것처럼 만드는" 패턴을 그대로 가져와, 5회 실패 후 `limiter.reset()`을 한 번 더 호출한 다음 올바른 비밀번호로 재시도해 423이 나오는지 확인하는 방식으로 해결(DB에 저장된 잠금 상태는 이 리셋의 영향을 받지 않는다는 점을 이용)
- 프론트엔드는 `LoginPage.jsx`의 `describeAuthError`에 423 분기를 추가해, 백엔드가 준 "15분 후 다시 시도해주세요" 같은 구체적인 안내를 그대로 보여주도록 함(기존엔 423도 401과 똑같이 "아이디 또는 비밀번호가 올바르지 않습니다"로만 보였음)
- 검증: pytest에 5회 실패 시 잠기는지, 4회는 잠기지 않는지(정상 로그인 가능), 성공 시 카운트가 실제로 DB에서 0으로 초기화되는지 확인하는 테스트 4개 추가 — 102개 전부 통과, `auth.py`·`routers/auth.py`·`models.py` 커버리지 100%. vitest 15개(423 메시지 분기 테스트 포함)·build·oxlint도 통과
- 로컬 서버로 실제 curl 5회 실패 → 백엔드 재기동(요청 속도 제한만 초기화, DB의 잠금 상태는 유지)→ 올바른 비밀번호로도 로그인이 막히는지 API 레벨에서 먼저 확인한 뒤, 같은 상황을 실제 브라우저에서 재현해 "로그인 실패 횟수를 초과해 계정이 잠겼습니다. 15분 후 다시 시도해주세요." 토스트가 정확히 뜨는 것을 화면으로 직접 확인. 마지막으로 Playwright E2E 5개를 재실행해 정상 로그인 흐름에 회귀가 없음을 재확인
