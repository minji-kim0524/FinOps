## `57d7b69` chore. 백엔드 의존성 취약점 점검 (pip-audit) - 실제 앱 의존성 4개는 이미 최신 버전이라 조치 불필요 확인 - CI에 pip-audit 비차단 단계 추가 - 로컬 venv setuptools/pip 업그레이드

- 수정 파일: `.github/workflows/ci.yml`

### 목적 및 이유
- 23단계(npm audit)에서 프론트엔드 취약점은 확인했지만 백엔드 Python 패키지는 아직 안 본 상태였어서, 이어서 `pip-audit`으로 점검
- `pip-audit -r requirements.txt`로 실제 앱 의존성만 감사(도구 자체의 의존성인 requests/urllib3/filelock/msgpack 등은 결과에서 제외)한 결과, `starlette`/`python-multipart`/`pytest`/`click` 4개 패키지에서 13건의 알려진 취약점이 나옴
- 하나씩 `pip index versions`로 실제 PyPI 배포 현황을 대조 확인한 결과, **네 패키지 모두 이미 PyPI에 올라온 최신 버전을 쓰고 있었음**. `requirements.txt`에 버전을 고정해두지 않은 덕분에 그동안 `pip install -r requirements.txt`를 새로 돌릴 때마다 항상 최신 보안 버전을 받아온 것으로 확인
- pip-audit가 제시하는 "수정 버전"(starlette 1.0.1, python-multipart 0.0.31, click 8.3.3 등)은 아직 PyPI에 실제로 배포되지 않았거나, starlette의 경우 FastAPI 자체가 `starlette<1.0.0`으로 상한을 걸어둔 상태라 지금 강제로 올리면 오히려 호환성이 깨짐을 확인 — 즉 우리가 놓친 패치가 아니라 상류 라이브러리 쪽에서 아직 패치가 안 나온 상태라 현재로선 조치할 방법이 없음
- 별개로 로컬 개발용 venv에 아주 오래된 `setuptools`(58.0.4, venv 최초 생성 시 딸려온 것)가 있던 걸 발견해 업그레이드. 실제 배포(Docker/Render)는 매번 `python:3.11-slim`에서 새로 빌드되므로 이건 로컬 위생 문제였을 뿐, 배포 환경에는 영향 없었음
- `ci.yml`: `pip-audit`을 CI에 **비차단(advisory)** 단계로 추가 — 지금처럼 "고칠 수 없는" 취약점이 있어도 빌드를 실패시키지 않고 로그에만 남겨서, 나중에 실제 패치가 배포되면 눈에 띄도록 함
- 검증: 로컬 venv의 pip/setuptools 업그레이드 후 pytest 36개 전부 통과(회귀 없음 확인)
