### 목적 및 이유
- AskUserQuestion으로 이번 세션 동안 가장 많이(10회 이상) 후보로 올랐던 "비밀번호 재설정(보안 답변) 무차별 대입 방어"를 드디어 사용자가 선택. 2026-09-19에 로그인 계정 잠금을 넣을 때부터 남아있던 공백으로, `/auth/password-reset`의 보안 답변 추측은 여전히 IP 기준 분당 5회 제한(slowapi)만 있어 여러 IP에 걸쳐 천천히 시도하는 공격에는 무방비였음
- 구현 방향을 정하며 가장 먼저 판단한 것: 로그인 실패용 카운터와 별도의 카운터를 새로 만들 것인가, 아니면 기존 `failed_login_attempts`/`locked_until`을 재사용해 "계정" 하나에 대한 단일 잠금으로 취급할 것인가. 후자를 선택 — 로그인이든 보안 답변이든 결국 "이 계정에 내가 모르는 값으로 들어가려는 시도"라는 점에서 같은 위협이고, 새 컬럼/마이그레이션 없이 2026-09-19에 만든 `is_account_locked`/`register_failed_login`/`reset_login_attempts` 헬퍼를 그대로 재사용할 수 있어 구현이 매우 단순해짐
- `backend/app/routers/auth.py`의 `reset_password`를 `login`과 정확히 같은 3단계 패턴으로 수정: (1) 계정이 이미 잠겨 있으면 보안 답변이 맞든 틀리든 423으로 즉시 차단 (2) 답변이 틀리면 실패 카운트 증가(5회째 잠금) (3) 맞으면 카운트를 초기화하고 비밀번호를 재설정. 결과적으로 로그인 3회 실패 + 보안 답변 2회 실패처럼 두 경로를 섞어 시도해도 5회째에 잠기고, 잠긴 동안은 로그인도 함께 막힘(카운터를 공유하므로 당연한 결과지만, 실제로 테스트에서 재확인)
- 프론트엔드는 로그인 폼에는 이미 423 처리가 있었는데 비밀번호 재설정 모달에는 없어서, 실제로 계정이 잠긴 상태로 재설정을 시도하면 "보안 답변이 올바르지 않습니다"라는 엉뚱한 메시지가 뜨는 것을 코드로 확인하고 수정. 두 곳(`describeAuthError`의 로그인 분기, `handleResetPassword`의 catch)에 거의 똑같은 "423이면 detail을 보여주고 없으면 기본 문구" 로직이 생기길래 `describeLockoutError` 헬퍼로 합쳐 중복 제거
- 검증: pytest에 (1) 보안 답변 5회 실패 시 올바른 답변을 넣어도 423인지, (2) 로그인 3회+재설정 2회처럼 실패 경로를 섞어도 카운터가 합산되는지, (3) 성공하면 DB의 카운트가 실제로 0/None으로 초기화되는지, (4) 재설정으로 잠긴 계정이 로그인도 함께 차단하는지 4개 추가 — 107개 전부 통과(커버리지 99% 유지, `routers/auth.py` 100%). 계정 잠금 테스트는 slowapi의 분당 5회 제한과 뒤섞이지 않도록 2026-09-19와 같은 방식(`limiter.reset()`으로 요청 속도 제한 창을 새로 시작한 것처럼 만들되 DB의 잠금 상태는 그대로 유지)으로 검증
- 프론트엔드는 vitest 48개(재설정 모달이 실제로 423을 받았을 때 안내 문구가 뜨고 모달이 닫히지 않는지 확인하는 테스트 1개 추가), build, oxlint 통과. Playwright E2E 5개도 재실행해 정상적인 비밀번호 재설정 흐름(보안 질문 조회 → 답변 → 재설정 → 새 비밀번호로 로그인)에 회귀가 없음을 확인
- README의 인증 기능 설명도 "로그인 5회 실패"에서 "로그인 또는 비밀번호 재설정을 합쳐 5회 실패"로 정확하게 갱신
