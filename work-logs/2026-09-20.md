# 2026-09-20

## `bbfcbdd` refactor. 라우터/훅 비대화 정리 - backend: calculate_bulk의 CSV 파싱/검증을 parse_bulk_upload_csv로 추출, 3곳에 반복되던 필터 쿼리 파라미터를 RecordFilterParams로, 집계 3종의 공통 조회를 get_owned_records_by_created_at으로 통합 - frontend: useSalaryRecords를 useRecordFilters/useRecordExports로 분리(App.jsx 반환 인터페이스는 동일하게 유지) - pytest 102개/vitest 15개/E2E 5개 그대로 통과

- 신규 파일: `frontend/src/hooks/useRecordExports.jsx`, `frontend/src/hooks/useRecordFilters.js`
- 수정 파일: `backend/app/routers/records.py`, `backend/app/services/records.py`, `frontend/src/hooks/useSalaryRecords.jsx`

### 목적 및 이유
- 사용자가 "현재 파일들의 코드를 분석해서 가독성을 높이고 중복을 제거해달라"며 예전(2026-09-04)과 동일한 5가지 기준(단일 책임, 중복 로직 공통화, 변수/함수명 명확화, 불필요한 import·Dead Code 제거, 리팩토링 후 무동작-변경 검증)으로 요청. 그때는 `main.py`/`App.jsx`라는 "God 파일" 자체를 구조 분리했었는데, 그 이후 두 달 가까이 여러 기능(bonus_pay, 이력 필터/정렬, CSV 템플릿, 급여명세서 ZIP, 로그인 계정 잠금 등)이 계속 붙으면서 이번엔 `routers/records.py`와 `useSalaryRecords.jsx`처럼 "새 구조 안의 특정 파일"이 다시 비대해져 있는 상태였음
- 먼저 Explore 서브에이전트로 backend/app, backend/tests, frontend/src 전체를 읽기 전용으로 감사시켜 근거(파일:줄번호) 있는 발견만 추리고, 억지로 더 쪼개거나 스타일 취향만 지적하는 항목은 배제하도록 지시. 그 결과 dead code나 불명확한 이름은 발견되지 않았고(grep으로 모든 export/변수 실사용 여부 재검증), SRP 위반·중복 2가지 범주에서만 구체적 항목이 나옴
- **백엔드**: `calculate_bulk`(52줄)가 라우터인데도 CSV 컬럼 기본값 채우기·타입 강제변환·행별 검증까지 직접 하고 있어서, `services/records.py`에 `parse_bulk_upload_csv(df) -> (valid_df, errors)`로 추출. `list_records`/`export_records`/`download_payslips_zip` 3곳에 그대로 반복되던 6개 필터 Query 파라미터 선언과 `apply_record_filters(...)` 호출 블록은 `RecordFilterParams` 데이터클래스로 묶어 FastAPI `Depends(RecordFilterParams)`로 라우터 시그니처를 단순화. `monthly_summary`/`yearly_summary`/`employee_summary`의 반복 조회는 `get_owned_records_by_created_at(db, owner_id)`로 추출
- FastAPI가 `@dataclass`를 쿼리 파라미터 의존성으로 정확히 해석하는지가 이번 리팩토링에서 가장 위험도가 높은 부분이었는데(잘못하면 body로 인식되거나 파라미터가 아예 안 먹을 수 있음), 실제로는 기존 pytest의 필터/정렬/export/ZIP 테스트들이 전부 그대로(수정 없이) 통과하는 것으로 검증
- **프론트엔드**: `useSalaryRecords.jsx`(293줄, state 20개·반환값 15개)가 ①필터/정렬/페이지네이션 ②집계 3종 조회 ③파일 다운로드 4종 ④CRUD까지 서로 다른 4가지 책임을 다 지고 있던 것을, `useRecordFilters.js`(검색·필터·정렬·페이지 상태 및 `buildFilterParams`)와 `useRecordExports.jsx`(엑셀/ZIP/CSV템플릿/PDF 다운로드 + CSV 업로드)로 분리하고, `useSalaryRecords.jsx`는 목록/집계 조회·CRUD를 유지하면서 이 두 훅을 조합만 하도록 재구성
- `App.jsx`가 소비하는 `salary.*` 반환 객체의 키를 하나도 바꾸지 않아, 리팩토링 후에도 **App.jsx는 한 줄도 수정하지 않음** — grep으로 `App.jsx`가 쓰는 모든 `salary.*` 속성이 새 반환 객체에 그대로 존재하는지 사전에 확인한 뒤 진행
- 검증: pytest 102개 전부 무수정으로 통과(커버리지 99% 유지, `services/records.py`는 새로 늘어난 코드까지 포함해 100%), vitest 15개·build·oxlint 통과, Playwright E2E 5개 통과. 추가로 로컬 서버를 띄워 정렬 클릭·ZIP 일괄 다운로드·엑셀 내보내기·CSV 템플릿 다운로드가 실제 네트워크 요청 레벨에서 리팩토링 전과 동일하게 동작하는지 브라우저로 직접 재확인(CSV 일괄 업로드는 파일 선택창 자동화가 번거로워 생략하고, 대신 pytest의 `parse_bulk_upload_csv` 관련 테스트 전체 통과로 갈음)
