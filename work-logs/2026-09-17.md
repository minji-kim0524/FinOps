# 2026-09-17

## `522913b` refactor. tax_table.py의 도달 불가능한 방어 코드 정리 - _lookup_over_top의 유일한 호출부가 이미 보장하는 경계 조건 재확인 제거 - 루프 끝의 잘못된 폴백(return base)을 도달 시 즉시 드러나도록 raise AssertionError로 교체 - pytest 99개 그대로 통과, 의도 설명 docstring 추가

- 수정 파일: `backend/app/tax_table.py`

### 목적 및 이유
- AskUserQuestion으로 제시한 후보(로그인 보안 강화, tax_table.py 도달 불가능한 방어 코드 정리) 중 사용자가 이 항목을 선택. 이전에 백엔드 테스트 커버리지를 처음 측정했을 때(2026-09-12) `_lookup_over_top` 내부의 두 줄이 계속 미검증으로 남아 있었는데, 당시엔 "현재 유일한 호출부(`_lookup_single`)의 조건상 도달이 원천적으로 불가능한 코드"라고 판단해 억지로 테스트를 채우지 않고 그대로 남겨뒀던 부분
- `grep`으로 `_lookup_over_top`의 호출부가 `_lookup_single` 단 한 곳뿐임을 다시 확인. `_lookup_single`은 `gross_pay > _TOP_GROSS_PAY`일 때만 `_lookup_over_top`을 호출하므로, 함수 내부에서 `if gross_pay <= _TOP_GROSS_PAY: return base`로 같은 경계를 다시 확인하는 코드는 실행될 수 없는 죽은 코드였음 — 제거
- 루프 끝의 `return base  # 도달하지 않음` 폴백도 함께 정리. `_OVER_TOP_TIERS`의 마지막 구간(87,000,000원 초과)은 상한(`upper`)이 `None`이라 어떤 `gross_pay` 값이 와도 루프 안에서 반드시 매칭되어 반환되므로, 루프를 다 돌고 이 줄에 도달하는 일은 없음. 게다가 이 폴백이 실제로 도달했다면 초과금액 계산 없이 `base`만 반환해 틀린 세액을 조용히 돌려줬을 코드였다는 점도 확인 — 죽은 코드인 데다 만약을 대비한 값조차 잘못돼 있었던 것. 단순 삭제 대신 `raise AssertionError(...)`로 바꿔, 앞으로 `_OVER_TOP_TIERS`가 실수로 잘못 수정돼(예: 마지막 구간에 상한을 넣는 등) 정말 이 지점에 도달하는 상황이 생기면 조용히 틀린 값을 내는 대신 바로 예외로 드러나도록 함
- 왜 경계 조건을 다시 확인하지 않아도 되는지를 나중에 읽는 사람이 알 수 있도록 함수에 docstring을 추가
- 검증: 코드 동작 자체는 바뀐 게 없어(죽은 코드/불가능한 폴백만 제거) `test_tax_table.py`에 이미 있던 경계값 테스트(9,999,999 / 10,000,000 / 10,000,001 / 15,000,000 / 50,000,000원 등)를 포함해 pytest 99개가 수정 없이 그대로 통과. `tax_table.py` 커버리지는 95%(미검증 2줄) → 98%(의도적으로 남긴 `raise AssertionError` 1줄만 미검증)로 개선
